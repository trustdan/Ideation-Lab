# Defense innovation lab

**Who it's for:** A DoD program office, service innovation cell, or defense S&T/acquisition
unit trying to adopt an emerging technology or a non-traditional pathway (OTAs, SBIR/STTR,
rapid prototyping) against program-of-record inertia and a risk-averse requirements process.
Participants span program management, requirements/acquisition staff, S&T staff, and, wherever
possible, an actual operator or end user.
**Outcome it produces:** One prioritized innovation bet — the capability gap it targets, the
pathway or partner type, and a near-term pilot with an owner and a decision date. Not a
technology roadmap; a bet the program office is willing to resource and be measured against.
**Envelope:** 1 day (~6 working hours) · 8–15 participants · in-person strongly preferred.

## Notes for the facilitator
- **Known failure mode #1:** the room converges on "run another study" or "do another
  demo" as a safe answer that avoids committing real resources to a pilot — this scenario's
  version of [[defense-contractor-strategy]]'s "chase more IDIQs." Provoke it in the HMW round.
- **Known failure mode #2:** requirements creep kills the bet before it's tried — a
  risk-averse stakeholder adds "it must also do X, Y, and Z" mid-session, quietly turning an
  innovative pilot back into a program-of-record. Use the premortem block to test whether the
  minimum viable pilot survives contact with the room's actual gatekeepers, and name creep
  explicitly if it happens live.
- Program-of-record staff may reflexively defend the existing solution against a disruptive
  alternative regardless of the alternative's merits — the same dynamic
  [[reorg-integration-clinic]] names as "our way was better" advocacy. Evaluate on capability
  gap evidence, not on which option's advocate is more senior.
- If no actual operator or end user is in the room, say so explicitly and treat the session's
  conclusions as provisional pending that input — a capability bet shaped only by acquisition
  and program staff risks solving the wrong problem well.
- Classification and competitive-sensitivity concerns can be used to shut down speculative
  discussion before it's tested against a real boundary. Pre-clear the room's actual
  discussion boundary in the session's Constraints, exactly as
  [[defense-contractor-strategy]] does — don't let it get litigated live.
